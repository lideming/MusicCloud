# DOM/CSS Canvas rendering and native sidebar material

The renderer paints an existing DOM subtree. DOM and CSS retain layout, native scrolling/sticky positioning, content hit testing, focus, accessibility and event handlers. Explicitly opted-in overlay scrollbar controls share the same DOM scroll offsets. Canvas2D produces reusable paint resources; WebGL composites them on a transparent output Canvas. No DOM screenshots, cloned page, custom scroll position or parallel business model are involved.

## Native material ownership

- MusicCloud creates `.sidebar-material` outside the source scroller, inside `#sidebar-shell`. This DOM element alone owns the external `backdrop-filter` and right border; its color fill is transparent in both themes. The filter samples the browser's actual underlying main-page DOM.
- Material starts at the shell's content edge. The mobile 200-pixel gesture padding stays outside the painted material. The shell retains existing pan/hide/peek transforms. Its exterior scrim is a managed child View, positioned at `left: 100%`, so it follows the same transform and shades only the area to the right of the sidebar. The glass does not sample that scrim; existing scrim opacity, click-to-close and drag behavior remain. Material and scrim end at the main container, above the bottom player.
- `#sidebar` has a transparent background. The output Canvas has no native-material pixels. On disposal/failure/context loss the material remains and ordinary DOM content becomes visible again; an opaque source background does not cover the glass.
- Internal headers have transparent backgrounds and ordinary CSS borders/shadows, with no second native backdrop filter. Their custom content blur only reads selected source-subtree paint resources, never the external material or main page.
- The application's light/dark translucent palette is defined globally, so sidebar, content and other items share the same hover/pressed/selected feedback without sidebar-only overrides.

## Generic renderer entry point

`new DOMCanvasRenderer(source, host)` paints a source subtree into its positioned host. The source and Canvas share the host's movement. The renderer owns Canvas positioning/pointer transparency, its root-only paint-suppression rule, observer/resource lifetime and restoration. The host owns its own background/material and native geometry. It must be a positioned containing block; the renderer does not alter the host's layout mode.

Callers provide no list/header arrays, semantic membership, z-index threshold or paint-pass configuration. `SidebarCanvas.ts` mounts the renderer, declares the sidebar's overlay scrollbar opt-in and adds the application's output class. Its core modules do not import application models, routers or view state.

- `DOMPaintTree.ts` derives paint-resource boundaries from DOM/computed CSS, native dimensions, explicit stacking contexts, sticky boxes and custom-effect/source boundaries. Small unfragmented subtrees reuse a surface; large scroll containers are split into their normal child subtrees. It preserves the block/flex/positioned stacking subset as a hierarchy: a high-z descendant cannot escape a lower-z context, and static flex/grid items get their context from their parent's layout mode.
- `DOMCanvasRenderer.ts` batches reads, tracks nearby resources with IntersectionObserver, reads only active resource/ancestor geometry on scroll, and evicts offscreen resources. Content/layout/style changes dirty resources; opacity/translation/scroll can reuse pixels. CSS shadows have separate cached raster resources so changing scroll shadows does not rerasterize foreground text. Root opacity applies once to the completed GPU output. Split opacity contexts use scoped, depth-reused compositor surfaces; nested opacity inside a cached resource is also composited once.
- `CanvasPaint.ts` paints solid backgrounds, borders/radii, inward focus outlines, native clipping, text, SVG and images from computed styles. Text ranges locate browser-measured lines; complete logical strings go through native Canvas shaping, including bidi, combining characters and joined emoji. Standalone SVG units use the same box/image path as embedded icons. Single outer CSS box shadows use Canvas2D shadow rasterization. Empty decorative `::before`/`::after` boxes are read from computed CSS, including their color, box dimensions and simple translation/scale; the drag marker has no application-specific paint overlay.
- `CanvasCompositor.ts` consumes an internal ordered content display list and transparent resource surfaces. It knows nothing about sidebar roles or native glass. Scoped opacity groups and regional blur are simple composition operations, not a dependency graph or shader configuration API. Normal CSS resources supply tint/foreground/shadow.

## Declarative content blur

`DOMCanvasEffects.ts` handles the renderer-only `data-canvas-blur` attribute separately from ordinary CSS painting. Its value contains CSS selectors scoped to the source root, identifying the DOM subtrees whose painted content is the blur input. Application initialization must set a real DOM attribute; the current webfx JSX attribute fallback assigns unknown keys as JavaScript properties.

- MusicCloud's login/settings header declares `data-canvas-blur="#sidebar-list ul, #sidebar-features"`.
- The playlist heading declares `data-canvas-blur="#sidebar-list ul"`.
- Their positions and paint order come from their native sticky layout and CSS stacking. The effect runs at that element's paint position, replaces sharp pixels only in its actual band, and then ordinary header CSS paints the crisp foreground.
- Blur uses a fixed separable Gaussian kernel. Offsets and sampling margins are CSS pixels, so DPR changes resolution rather than radius. Work is restricted to the actual band and its sampling margin.

Native drag images reuse cached paint surfaces, while existing DOM handlers own reordering. These browser decorations are not a full native-widget renderer.

## Overlay-only scrollbars

Set a real `data-canvas-scrollbar="overlay"` attribute on each scroll element that needs visible scrollbar controls during Canvas takeover. The root and ordinary nested viewports use the same mechanism; `new DOMCanvasRenderer(source, host)` remains the entry point. The existing content DOM is unchanged: there is no viewport/content wrapper, replacement scrolling model or hidden-overflow takeover.

- `OverlayScrollbars.ts` temporarily owns inline `scrollbar-width: none !important` and `scrollbar-gutter: auto !important` on opted-in elements before the first geometry measurement. Thus an ordinary desktop thin scrollbar's reserved 10-pixel gutter is removed from layout; the Canvas and content fill the viewport. The source retains its authored overflow behavior and native scrolling. Original inline property values/priorities are restored when ownership ends, leaving unrelated author changes intact. An originally absent style attribute is removed again when no other inline style remains. The declaration itself stays caller-owned.
- One 8-pixel style overlays the right/bottom viewport edges. A proportional thumb uses a 24-pixel minimum when space permits; two axes share a corner without overlapping tracks. Colors use the computed `scrollbar-color` RGB/RGBA pair when available, otherwise a translucent gray thumb and transparent track. This does not reproduce an operating-system scrollbar theme. There is no classic-gutter mode or separate width/style API.
- A single read-phase measurement supplies both the GPU solid rectangles and the transparent DOM hit surfaces in `.dom-canvas-scrollbars`, outside the suppressed source. Track/thumb clipping uses the same viewport/ancestor clip rectangles. The controls appear only after the matching Canvas frame succeeds. No-overflow axes lose their controls, and a collapsed root viewport hides the layer and releases capture. Source-root opacity applies to the completed output, including scrollbar paint, once.
- Pointer capture handles mouse/touch dragging and up/cancel. Dragging and track clicks write the intended element's existing `scrollTop`/`scrollLeft`; a track click centers the thumb at the chosen point. Native RTL horizontal offset zero displays the thumb at the right edge, and dragging left writes negative native offsets. There is no copied scrolling position, inertia or event polling.
- Ordinary content keeps native mouse/touch/wheel/keyboard input and existing click/context-menu/pan handlers. Only control rectangles receive scrollbar pointer input, without activating rows underneath; wheel over a control forwards deltas to its real scroller. Original DOM focusability and keyboard/accessibility behavior remain. The extra pointer hit surfaces are not additional tab stops or duplicate accessibility widgets.
- Nested opted-in scroll viewports create paint-tree boundaries rather than baking the whole scrolling subtree into a parent surface. Captured native scroll events schedule current geometry/clipping; nearby child resources can reuse their pixels. A viewport ResizeObserver and existing mutation/resource-size notifications update overflow geometry. No idle animation loop is added.
- Dispose, initial paint failure and context loss release pointer capture, remove the control layer and restore native scrollbar styles. Constructor failure before ownership leaves native bars untouched; failure during ownership uses the same cleanup path. Detached or no-longer-opted-in nested elements also release their overrides. Runtime state is kept in the helper, not extra activation attributes or a parallel stylesheet override.

Visible scrollbar chrome is supported through this explicit overlay contract. Unopted-in scrollers keep their authored layout; their native chrome is suppressed along with other source paint and is not reconstructed as a classic scrollbar. Declare overlay mode on each viewport that requires visible controls. Advanced writing modes, arbitrary transforms and operating-system widget behavior remain outside this phase's scrollbar subset.

## Text raster precision

- Snapshot reading and cache validation share fractional, untransformed border-box dimensions, including content-box padding/borders. Integer `offsetWidth`/`offsetHeight` fallback is used only when computed dimensions are unresolved. Fractional layout is not mistaken for a CSS scale.
- Foreground and shadow placement retain the allocated raster extent divided by DPR, including the transparent padding from `ceil` allocation. Unscaled cached surfaces align their origins to the Canvas physical-pixel grid; intentional CSS scale keeps fractional geometry and linear sampling. Cached foreground resources record their DPR and are refreshed when it changes.
- This removes demonstrated extra resampling at DPR 1, 1.25 and 2 without a phase-aware cache or idle animation loop. Native baseline/subpixel-phase differences can remain; arbitrary output-target scaling is unchanged.

## Lifetime and inspection

Source DOM paint is suppressed only after a successful complete frame. Descendant computed opacity remains logical; source-root opacity is read with suppression temporarily removed during the read phase and restored synchronously. Own suppression records are ignored, avoiding an observer feedback loop. `dispose()` restores DOM paint, disconnects observers/listeners and releases resources. Missing WebGL, image/CORS failures, upload/raster errors and context loss retain or restore DOM rendering. Lost contexts do not automatically retry.

There is no idle animation loop. Events/mutations/resize/scroll schedule a frame; only running finite CSS transitions/animations sustain more frames. Shared-host placement-only style updates reuse pixels, while inherited host colors/fonts/custom properties invalidate them. `stats` reports frames, snapshots, foreground rasterizations, decoration rasterizations and current cached foreground resources.

## Supported subset and remaining scope

The implemented subset covers the maintained sidebar and unrelated ordinary block/flex/positioned subtrees without a custom binding. It is not a complete browser paint implementation. Arbitrary rotations/perspective, gradients/background images, general filters, multiple/inset shadows, generated text pseudo-content, complex floats/inline/negative-z interactions and the full range of CSS blending/stacking combinations are outside this phase's validated subset. Decorative pseudo boxes support the explicit simple box geometry needed here, not arbitrary generated layouts. Large painted container backgrounds beyond the visible-resource cases have not been qualified as a general-purpose tiling system.

Canvas follows main-thread native scroll notifications; it does not add an independent compositor-thread scroll implementation. Cross-origin images need a Canvas-readable server CORS policy; unreadable images restore the entire native source rather than leaving a partially missing surface. Native drag-ghost visual parity and iOS/Safari/device behavior remain device follow-up, not a claim from synthetic drag events.

## Validation

- Build: `pnpm run build:typecheck` and `pnpm run build:bundle`.
- Tests: `node --test tests/*.test.cjs` with Node 22+ and Chromium (`CHROMIUM_PATH` overrides `/usr/bin/chromium`). Tests use a temporary local server with the real production bundle and no backend account. Set `TMPDIR=/data/musiccloud-canvas-work` in the maintained lab; other environments use their normal temporary directory.
- Production checks cover actual visible list pixels, bounded nearby caching, zero idle frames, scroll/pan reuse, mouse hit/press, dynamic names/playing state, text/SVG/avatar/theme/empty state, disposal and actual context loss. Both production header attributes are checked, and removing the top-header effect increases actual GPU edge contrast. Native glass is tested by comparing browser-composited stripe contrast with the material filter enabled/disabled and by checking transparent Canvas output and retained material after disposal.
- An unrelated root/host check covers static flex-item z-index, nested contexts, source-root opacity once, group opacity across resource boundaries and direct SVG decode/paint without sidebar classes or binding.
- Mobile scrim checks compare browser-composited pixels in both themes: the sidebar backdrop stays bright while outside content is dimmed. Real touch pan keeps the scrim aligned to the shell edge, outside clicks close the sidebar, and fade completion removes the scrim.
- Overlay checks start with a desktop Chromium thin scrollbar that reserves 10 pixels, then verify zero-gutter Canvas geometry, real mouse thumb/track input without row activation, native wheel and mobile resize. They verify authored inline `!important` values/priorities and native gutters after dispose/context loss, unavailable WebGL and failed initial paint. Unrelated DOM checks exercise horizontal LTR/RTL, nested mouse/touch scrolling with actual changed Canvas pixels, pointer cancellation, PageDown, no overflow, a collapsed root viewport and detached-scroller cleanup.
- Raster precision checks preserve actual alpha texels at DPR 1/1.25/2, demonstrate fractional-extent/half-pixel resampling, and exercise fractional content-/border-box layout, DPR changes, shadow offsets, cache reuse and intentional scale/release through the real renderer.
- GPU checks retain sharp pixels outside the effect band, replace sharp pixels within it, exclude unselected background, preserve crisp foreground and compare CSS-space blur at DPR 1 and 2. Existing player regressions run in the same 25-test suite.

Chrome checks are separate from the deferred Mac/iOS environment. Device verification will resume when that environment is available.
